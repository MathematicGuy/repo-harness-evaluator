# HTML Explainer Format

The explainer is a single self-contained HTML file written next to its source `REPORT.md` as `REPORT.html`. Tailwind and Mermaid both come from CDNs (mermaid@11 ESM, theme `neutral`); there is no other JavaScript — no toggles, no app code, no interactivity beyond Mermaid's own rendering. The page is TWO STACKED SECTIONS plus a method appendix, reachable via a sticky anchor nav.

**Ordering principle:** novel information first (Sections A and B change every audit run), repeated information last (Section C is identical every run — new readers scroll down once; veterans stop at B6 and never re-read it).

Header shows: report title, audit date, purpose profile in one line (e.g. "MVP — 4-week delivery"), evaluation depth. No introduction paragraph in the header — A1 handles that.

## Palette & badge conventions

- **emerald** (`#10b981`) — pass / excellent / sufficient / "keep" / after-state
- **amber** (`#f59e0b`) — adequate / partial / warning / "do soon"
- **red** (`#dc2626`) — deficit / failed gate / risk / friction edges in flowcharts
- **indigo** (`#6366f1`) — neutral accent, links, technical highlights
- **dark gradient** (`#0f172a → #1e293b`, the `.hero` class) — capability-rank card only
- **slate** — deferred / unchanged / informational badges

Flowchart conventions (used in B1):

- **red dashed edge** = friction / broken step in the CURRENT flow, tagged with its finding ID (`[F-xx]`) and anchor-linked to the matching finding card in B4
- **emerald solid node** = fixed / added step in the IMPROVED flow
- **slate node / badge** = unchanged step, or a deferred fix (still drawn in the improved flow, honestly labelled "deferred")

## Section A — For Decision Makers (`id="verdict"`)

Plain language, ~one screen of scrolling. Answers: what, why, input, output, result, next.

- **A1 — What is this?** One short paragraph: before the team (and its AI coding assistants) builds features, we need confidence that the project's working setup — tests, documentation, automation, safety rules — is strong enough for its purpose; this report is a health check of that setup, called the "harness". Below it, a small bordered analogy card: *"Think of it as a pre-flight checklist for the project, not a review of the code's features."*
- **A2 — Why we need it.** 3–4 bullets, business framing: catch setup weaknesses before they slow the team down; make AI assistants safe and productive; give a realistic read on delivery risk; produce a shared evidence-based picture, not opinions.
- **A3 — What we looked at.** A 6-tile icon grid, one line per tile, plain concepts never file paths: Automated tests · Documentation & handoff notes · Build & setup steps · Safety & secrets handling · AI-assistant rules · Progress tracking & decisions.
- **A4 — The verdict.** Three big score cards side by side: FITNESS FOR PURPOSE (score/100 + rank, emerald-tinted when fit), HARNESS CAPABILITY (score/100 + rank, on the dark-gradient hero card), OVERHEAD (score/40 + level, amber-tinted when moderate). Under each card, a one-line plain-language translation, e.g. "The setup matches what a 4-week MVP actually needs." / "Solid foundations; some automation still manual." / "The process adds only a little extra effort."
- **A5 — What this means.** Traffic-light summary, three rows with coloured dots: emerald **Strong** (what works), amber **Watch** (what needs attention), red **Gap** (what is missing). Derive rows from the scorecards and findings, translated to plain language.
- **A6 — What we do next.** A prioritised table with three groups: **DO NOW** (with effort estimates, e.g. "~10 min, low risk"), **KEEP DOING** (labelled "working well"), **LATER** (labelled "deferred" with the trigger). Source: the report's lifecycle roadmap.
- **A7 — Bottom line.** A single emerald callout box, two sentences max: overall verdict plus the one action that matters most.

**Tone rule for Section A:** no jargon anywhere. Never write "harness dimension", "E4", "adequacy", or "capability rank" in this section — translate everything ("no live monitoring once the app is running", not "observability deficit").

## Section B — For Engineers (`id="engineers"`)

Technical and repo-specific — everything here is rebuilt from evidence on every audit run.

### B1 — How this repo's harness works today (the centrepiece)

TWO stacked Mermaid `flowchart TD` diagrams, each wrapped in a `rounded-lg border border-slate-200 bg-white p-4` card:

1. **Current flow (as-is)** — the working session end to end (session start → read context files → open slice docs → pick owned paths → edit → narrow verify → full quality gate → CI → deploy → handoff update). Each friction point is a red dashed edge to a red-outlined node describing the failure, tagged `[F-xx]` and wrapped in a click/anchor link to its finding card in B4.
2. **Improved flow (after applying findings)** — same shape; red edges gone; each fix is an emerald node at the step where it lands. Deferred fixes are still drawn but carry a slate "deferred" label so the target state stays honest.

Worked example (adapt node names to the audited repo; keep the classDefs):

```html
<div class="rounded-lg border border-slate-200 bg-white p-4">
  <pre class="mermaid">
    flowchart TD
      S[session start] --> A[read AGENTS.md]
      A --> D[open slice docs]
      D -.->|stale path trap F-01| X1[docs say apps/api,<br/>folder is apps/backend]
      D --> P[pick Owned Paths] --> E[edit module code]
      E -.->|no boundary lint F-02| X2[cross-module import<br/>passes silently]
      E --> V[narrow verify] --> Q[pnpm quality] --> CI[CI gate] --> DEP[deploy]
      DEP -.->|no logs F-03| X3[health endpoint only]
      DEP --> H[update ExecPlan / handoff]
      classDef friction stroke:#dc2626,stroke-width:2px,stroke-dasharray:4 4,color:#dc2626;
      classDef fixed fill:#d1fae5,stroke:#10b981,stroke-width:2px;
      classDef deferred fill:#f1f5f9,stroke:#64748b,color:#475569;
      class X1,X2,X3 friction
      click X1 "#f-01"
      click X2 "#f-02"
      click X3 "#f-03"
  </pre>
</div>
```

In the improved-flow diagram, use `class N fixed` for applied fixes and `class N deferred` for deferred ones, with node text like `boundary lint — deferred (team ≥ 4)`.

Under both diagrams, a **what-changed strip**: one row per finding mapping finding → flow step → timing (e.g. "F-01 stale paths → fixed in docs → DO NOW", "F-02 boundary lint → added at edit step → DEFER (team ≥ 4)").

### B2 — Scores vs targets

Ten dimension bars, hand-built divs — not Mermaid. Each bar: dimension name + weight (`text-xs uppercase tracking-wider`), a `bar-track` with a filled bar for the actual score (scale 0–4) and a thin vertical marker at the target. Fill colour: emerald when actual ≥ target, red when actual < target. Print actual and target numerically beside each bar. Footnote below the block: *"Capability above target earns no extra fitness credit."*

### B3 — What we actually ran

Monospaced table (`font-mono text-sm`) of the dynamic tests actually run, from the report's Tests table: test name, result, time, evidence level, conclusion. Only tests actually executed belong here; static checks (greps, config inspection) get their evidence level shown so the distinction is visible.

### B4 — Findings

One card per finding, `id="f-xx"` (lowercase, matching the anchors used by B1's red edges). Each card: finding ID + title, severity badge (Critical/High = red, Medium = amber, Low = slate), evidence level, one-line observed evidence, the fix, and action timing (DO NOW / DEFER + trigger).

### B5 — Fit gates & coverage

Compact two-column block: fit gates with PASS (emerald) / FAIL (red) / N/A (slate) chips and the cap each gate would apply if failed; requirement coverage percentage with the verified/partial/unverified split; audit confidence with its depth ceiling noted.

### B6 — Method notes & limitations

Small text (`text-sm text-slate-600`), honest, bulleted — taken directly from the report's Limitations section: environment workarounds, what was simulated rather than verified live, which branch was audited. No spin.

## Section C — How the evaluation works (`id="method"`, appendix)

**This section is IDENTICAL every run** — copy it verbatim between runs; only Sections A and B are regenerated. It lives at the end on purpose.

### C1 — The fitness loop

```html
<div class="rounded-lg border border-slate-200 bg-white p-4">
  <pre class="mermaid">
    flowchart LR
      P[purpose] --> T[target] --> EV[evidence] --> TS[test] --> SC[score]
      SC --> FR[friction] --> CH[challenge] --> RP[report]
      classDef step fill:#f8fafc,stroke:#64748b,color:#0f172a;
      class P,T,EV,TS,SC,FR,CH,RP step
  </pre>
</div>
```

Under the diagram, one sentence per node in a small monospaced-labelled list: **purpose** — profile the repo's actual goal; **target** — set per-dimension capability targets for that purpose; **evidence** — collect artifacts, graded E0–E4; **test** — run dynamic checks where possible; **score** — rate each dimension 0–4; **friction** — price the harness's cost as overhead; **challenge** — subagents cross-examine the conclusions; **report** — publish scores, findings, and a roadmap.

### C2 — The scoring model

Formula card, monospaced (`font-mono text-sm`, on a white bordered card):

```text
capability = Σ (weight × score / 4)      10 dimensions, scored 0–4 each
adequacy   = min(actual / target, 1)     no credit above target
fitness    = weighted adequacy − overhead penalty
```

Beside or below it, two small rank tables: **fitness** — Excellent Fit (90–100) / Strong Fit (80–89) / Adequate Fit (65–79) / Misaligned (45–64) / Poor Fit (0–44); **capability** — S (90–100) / A (80–89) / B (65–79) / C (45–64) / D (25–44) / E (0–24). Keep both tables compact, `text-xs`.

### C3 — The evidence ladder

Five stacked full-width bands, darkest at the top = strongest:

```html
<div class="space-y-1">
  <div class="rounded px-4 py-2 text-white" style="background:#0f172a">E4 · direct dynamic proof — we ran it</div>
  <div class="rounded px-4 py-2 text-white" style="background:#334155">E3 · executable static proof — configs, lockfiles</div>
  <div class="rounded px-4 py-2 text-white" style="background:#64748b">E2 · repository documentation</div>
  <div class="rounded px-4 py-2 text-slate-800" style="background:#cbd5e1">E1 · naming / convention</div>
  <div class="rounded px-4 py-2 text-slate-600" style="background:#f1f5f9">E0 · assumption</div>
</div>
<p class="text-xs text-slate-500 mt-2">A score of 3+ requires at least E3 evidence.</p>
```

## Style guidance

- Lean editorial, not corporate dashboard. Generous whitespace between blocks; `space-y-16` between sections, `space-y-10` inside them.
- `text-xs uppercase tracking-wider` for schematic labels (dimension names, card headers, badge text) — they should read as schematic, not as UI.
- Keep diagrams ~320–400px tall; two B1 diagrams stack vertically, never side by side.
- Colour sparingly: the palette above and nothing else. Most of the page is stone/slate; colour marks meaning.

## Tone

Two registers, strictly separated:

- **Section A — plain English.** Short sentences. Business outcomes, not mechanisms. Analogies allowed (pre-flight checklist, health check). If a term needs a glossary, it doesn't belong in Section A.
- **Section B — precise and technical.** Use the evaluator's glossary terms exactly: *fitness*, *capability*, *adequacy*, *overhead*, *evidence level*, *fit gate*. No hedging, no "it's worth noting that". Bullets over paragraphs; if a sentence could be a bullet, make it a bullet.
